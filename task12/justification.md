JUSTIFICATION

The task was hardened on three levers. On localization, instruction.md no longer hands over the reproduction case: the title dropped the word "Continuous" ("tickMinStep Ignored for Some Continuous Scales" to "tickMinStep Ignored for Some Scales"), the body no longer names the configuration ("a left-oriented axis for a linear scale whose domain spans 0 to 12, with a minimum tick step of 3"), the closing line that previewed the corrected output ("every rendered tick step should be at least 3 (e.g., 0, 3, 6, 9, 12, rather than a smaller spacing)") was deleted, and the sentence that named the affected scale family ("ordinary continuous numeric scales (such as linear)") was removed. What is left is the symptom, the minStep value of 3, the requirement that it hold whether the domain ascends or descends, and the log/time out-of-scope note that matches the p2p exclusion tests. On visual reliance, the axis orientation, the domain 0 to 12, the scale kind and the buggy step of 2 now exist only in bug.png, so the agent cannot rebuild the repro case without opening the poster; visual_essentiality was raised from "helpful" to "essential" and difficulty_explanation was rewritten to name those three facts, replacing the old text that admitted the screenshot was "helpful confirmation rather than strictly required for diagnosis". On anti-cheat and scoring, test.sh computed a rubric verdict that it never passed to the verifier, so the rubric could not influence the reward at all; test.sh now calls verifier.py with --rubric and verifier.py consumes it, where a failed rubric can only withhold a 1.0 by capping the run at 0.5 and never forces a 0.0 on its own. verifier.py also writes /logs/verifier/reward.json as a flat map, so trial results now report each f2p and p2p individually instead of a single mean. The golden fix, test.patch, config.json, the evidence chain and the Dockerfile were left untouched. Re-validated: oracle 1.0, nop 0.0, harbor check now passes "Behavior In Task Description" (it failed before), and the Opus trial fails at 0.0 with all 3 f2p failing and all 7 p2p passing, with the analyzer confirming no reward hacking and a sufficient specification.


FEEDBACK FOR THE PREVIOUS CONTRIBUTOR

The harness side was in good shape, so the gap was the prompt. instruction.md described the whole reproduction case in text (linear scale, left-oriented axis, domain 0 to 12, minStep 3) and then showed what the fixed output should look like, "0, 3, 6, 9, 12", which the guidelines rule out twice: no named mechanism and no corrected-output preview. With the numbers in the text, the screenshot added nothing to the diagnosis, and the difficulty_explanation said so in its own words while still leaving visual_essentiality at "helpful", so the task shipped knowing it was under-hardened rather than fixing it. The harbor check caught the consequence directly, failing "Behavior In Task Description" because the blanket rule stated in the text would push an agent to enforce minStep on log and time scales too, the opposite of what three of the p2p tests require. The habit worth carrying forward: put the concrete repro values in the poster and keep only the symptom plus the scope boundaries in the text, then check that the boundaries you state match the p2p list. Two smaller items: test.sh computed a rubric verdict that verifier.py never received, so the rubric was dead weight in the scoring path, and verifier.py wrote only reward.txt, which left the trial report with one aggregate number and no way to see which f2p failed. Also clear stray files (tests/.gitkeep, tests/__pycache__) out of the bundle before submitting. The Dockerfile work was solid, cloning at base_commit and then stripping .git and re-initialising a single-commit history tagged harbor_base, which is what kept the agent from reading the fix PR.
