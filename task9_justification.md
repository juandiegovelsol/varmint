# Task 9 — flutter__flutter-181500-mm

## Justification of changes

**1. instruction.md — scope of the ask (localization lever, re-calibrated).**
Before, the prompt said only that "several day markers in this calendar dialog are circular when they should not be" and asked to "use the correct cell outline". It never said the outline shape is supposed to come from the calendar's theme, and never said the shape has to apply everywhere a day cell is drawn. That is a problem because the suite has three f2p tests — the selected-day background, the "today" border, and the day ink splash — so two of them checked behavior the prompt never asked for. Harbor's `behavior_in_task_description` check failed for exactly this reason, and the trial confirmed it: the agent produced a real, correct fix for the selected day and the today border, left the `InkResponse` alone, and scored 0.5. The new text states the symptom as "day markers are always plain circles, even though the calendar's theme is meant to control that outline shape" and asks for the shape to be used "everywhere that shape is drawn". No file path, no property or API name (`dayShape`, `ShapeDecoration`, `customBorder`), and no repo trace were added, so localization stays exactly as hard — the agent must still read the poster and find `_DayItemState` on its own. The change only makes the scope of the ask match the scope of the tests, so a complete fix is now the only thing that scores 1.0 and a partial one fails for the right reason.

**2. environment/Dockerfile — dropped the explicit `python3 python3-pip` install (anti-cheat / image hygiene).**
`pip` is not used by anything in the bundle, and installing an interpreter in the same `apt-get` line as the repo's build toolchain makes it look like a test-only dependency baked into the agent-facing image. The verifier's Python still arrives transitively with the GTK/glib dev packages already installed for building the repo, so `test.sh`, `judge.py` and `verifier.py` keep running unchanged. This must be re-confirmed by an oracle/nop re-run before submitting (see the note at the end).

**3. tests/judge.py — full file context for the rubric judge (anti-overfit).**
Before, the judge request carried only the criteria and the candidate diff, which gives about three lines of context per hunk. That is often too little to decide a criterion that the change actually satisfies (for example "the helper is defined in the same module"), producing a false 0. The judge now also gets `changed_files.txt`, the full current text of every file the diff touched, bounded at 200 KB, and the prompt documents what the judge deliberately does not get: the task instruction, the golden `fix.patch`, `test.patch`, the images, and browse access to the repo. Withholding the golden fix is the important part — a judge that can see it stops judging the criterion and starts checking similarity to one implementation, which is the overfitting the rubric exists to prevent. `rubrics.json` currently holds the always-pass placeholder, so this does not change today's reward; it makes the rubric path correct for any criterion added later.

## Feedback for the previous contributor

The hardening went one step too far on `instruction.md`: stripping it down to "circular … correct cell outline" removed not only the recipe but the scope of the ask. Three f2p tests require the themed shape in three separate places (selected endpoints, today border, ink splash), while the prompt implied only one, so `behavior_in_task_description` failed and the trial agent lost 0.5 on a genuinely correct partial fix — a failure caused by the prompt, not by the agent. The rule of thumb is to strip the *where* and the *how* (file lists, property and API names, step-by-step mechanism) but never the *what*: every f2p must map to a behavior the instruction or the poster actually asks for. Two smaller points: the Dockerfile installed `python3`/`python3-pip` that the repo's own build toolchain already brings in (and `pip` is never used), and `judge.py` handed the rubric judge only the diff hunks, which can fail criteria the submitted change actually satisfies.
