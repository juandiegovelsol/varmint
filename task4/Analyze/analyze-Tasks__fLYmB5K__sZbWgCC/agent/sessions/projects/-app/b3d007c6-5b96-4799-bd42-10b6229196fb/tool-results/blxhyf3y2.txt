5. Problem Solving:
   - Solved (root cause substantially identified, pending final confirmation and fix): The bug stems from an inconsistency between how the angle-axis "offset" (needed to center category labels/tooltip sectors correctly within their band, for a categorical `scaleBand`-based angle axis) is computed for (a) rendered axis tick labels (`combineAxisTicks` in axisSelectors.ts) and tooltip-tick lookup (`combineTicksOfTooltipAxis` in tooltipSelectors.ts) — both of which explicitly flip the offset's sign based on `mathSign(axisRange[0] - axisRange[1])`, i.e., based on whether the angle axis range increases or decreases — versus (b) the drawn Radar polygon vertices (`computeRadarPoints` in Radar.tsx), which add `angleBandSize` sourced from `getBandSizeOfAxis` (ChartUtils.ts), a function that returns `scale.bandwidth()` directly and is ALWAYS NON-NEGATIVE, with no sign/direction awareness at all.
   - Empirically confirmed via `node -e` scriptlets against `victory-vendor/d3-scale`'s `scaleBand` that raw `scale.map(category)` values differ from rendered axis tick-label coordinates by exactly one full bandwidth step (offset), and that this offset's sign flips with axis-range direction in the label/tooltip code paths but not in the polygon-drawing code path.
   - Confirmed via multiple full-DOM-render experiments (varying `startAngle`/`endAngle`: default 90/-270, reversed -270/90, 0/360, 360/0, 45/405, -90/270, 270/-90, and the `reversed` prop) that:
     - For the DEFAULT decreasing-direction configuration (90→-270, the built-in RadarChart default), the drawn polygon and axis tick labels HAPPEN TO AGREE (sign combination cancels out favorably), and hover-sweep tests (at 15° or 30° increments) resolved tooltips consistently to the correct/expected nearest label in that config.
     - For INCREASING-direction configurations (e.g., 0→360, or reversed prop, or other reversed start/end orderings), the drawn polygon's vertex-to-label correspondence becomes WRONG (e.g., for 0→360, the polygon's "North" vertex renders at the TOP of the chart while the "North" axis tick label renders at the BOTTOM), directly reproducing the visual bug in `mismatch.png`. Hover-sweep tests in these configurations also showed inconsistent tooltip resolution relative to the rendered labels, reproducing `bug.png`.
   - This directly explains the user's reported symptom fully: the axis labels and tooltip-hit-testing are mutually self-consistent (since they share the same offset formula/tick set), but the DRAWN SHAPE is the odd one out, using a sign-insensitive `angleBandSize`. (Note: this is somewhat in tension with the user's framing that hover ALSO disagrees with labels in bug.png; this is explained by the fact that the specific chart in bug.png may be using a non-default start/end angle configuration or `reversed`, OR — since the drawn shape is wrong, a user visually associates the WRONG shape with a label, and then hovering "near what looks like it should be a given series' point" naturally resolves to a different series than expected purely because the shape itself was mis-plotted; all three symptoms trace back to the single point-computation defect once you also account for label/tooltip already being correct/self-consistent in isolation).
   - STILL OPEN / NOT YET DONE: I have not yet written or applied the actual code fix. The most promising fix direction (not yet implemented) is to make `computeRadarPoints`'s `angleBandSize` (or `getBandSizeOfAxis`/`selectBandSizeOfAxis` upstream) direction-aware — i.e., apply the same `mathSign(axisRange[0] - axisRange[1])` sign flip to `bandSize` before adding it to `scale.map(name)` in Radar.tsx, so that it matches the sign convention already used by `combineAxisTicks`/`combineTicksOfTooltipAxis`. Alternatively, the fix could standardize all four "tick generation" implementations (the "four horsemen") to share a single, correctly-signed offset computation, and have `computeRadarPoints` consume that same correct value rather than reimplementing its own (via `getBandSizeOfAxis`, which is sign-unaware). This exact code change has NOT yet been written/tested; further work is needed to: (a) decide the precise fix location(s) — likely `getBandSizeOfAxis`/`selectBandSizeOfAxis` (to make bandSize signed) OR directly in `computeRadarPoints`/`Radar.tsx` (to apply the correct sign when adding `angleBandSize`) — while being careful not to break other consumers of `getBandSizeOfAxis` (e.g., Cartesian bar/line charts, `RadialBar.tsx`, `barSelectors.ts`, `lineSelectors.ts`, `areaSelectors.ts`, `radialBarSelectors.ts` all use it and must not regress); (b) verify the fix holds for arbitrary category counts (not just 4) and arbitrary start/end angle pairs (not just the handful tested); (c) verify RadialBar (which also uses polar angle axis with categorical bands, per `radialBarSelectors.ts`'s own `selectPolarGraphicalItemAxisTicks(state, 'radiusAxis', ...)` usage — note RadialBar's categorical axis is typically the RADIUS axis, not angle axis, so it may be a different/lower-risk code path, but should still be checked) is unaffected or also fixed if it has an analogous issue; (d) clean up or replace the scratch `/app/test/chart/repro.spec.tsx` file with a proper permanent regression test (e.g., in `test/polar/Radar.spec.tsx` or `test/chart/RadarChart.spec.tsx`) verifying polygon-vertex-angle vs. tick-label-coordinate vs. tooltip-hover-resolution consistency across several start/end angle configurations and category counts; (e) run the full test suite to confirm no regressions.
